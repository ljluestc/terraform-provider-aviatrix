# Unit Test Framework Expansion and Integration PRD

## Project Overview
Expand the newly implemented unit test framework to cover all major Terraform provider resources, integrate with CI/CD pipelines, and establish comprehensive testing standards for the terraform-provider-aviatrix project.

## Background
A comprehensive unit test framework has been successfully implemented with templates for CRUD operations, schema validation, input validation, error handling, and state management. The framework is validated and working with smoke tests on the Account resource. The next phase involves expanding coverage to all resources and integrating with development workflows.

## Goals and Objectives

### Primary Goals
1. Achieve 80%+ unit test coverage across all Terraform resources
2. Integrate unit tests into CI/CD pipeline with automated reporting
3. Establish unit testing as standard practice for all new resource development
4. Create resource-specific test suites for top 20 most-used resources
5. Document testing standards and provide developer training materials

### Success Metrics
- All existing resources have basic unit test coverage (schema + validation)
- CI/CD pipeline runs unit tests in < 2 minutes
- Code coverage reports generated automatically on every PR
- Zero regression in schema validation across releases
- 100% of new resources include comprehensive unit tests before merge

### FR-3: CI/CD Integration
**Priority: High**

#### FR-3.1: GitHub Actions Workflow
Create new workflow: `.github/workflows/unit-tests.yml`

Requirements:
- Run on every push and PR
- Execute in parallel with acceptance tests
- Complete in < 2 minutes
- Generate coverage reports
- Upload coverage artifacts
- Fail PR if coverage drops below threshold (70%)

Workflow steps:
1. Checkout code
2. Setup Go environment
3. Install dependencies
4. Run unit tests with coverage
5. Generate coverage report (HTML and XML)
6. Upload coverage to artifact storage
7. Comment coverage summary on PR
8. Fail if coverage threshold not met

## Non-Functional Requirements

### NFR-1: Performance
- Unit tests must complete in < 2 minutes for full suite
- Individual test files must run in < 1 second
- No external API calls in unit tests
- Parallelizable test execution
- Minimal memory footprint

### NFR-2: Maintainability
- Test code follows same quality standards as production code
- DRY principle applied using templates and helpers
- Clear test organization and naming
- Self-documenting test cases
- Easy to update when resources change

### NFR-3: Reliability
- Tests are deterministic (no flaky tests)
- No dependencies on external services
- No time-based assertions that could fail
- Proper test isolation
- Clean state between tests

### NFR-4: Developer Experience
- Clear error messages on test failures
- Easy to run tests locally
- Fast feedback loop
- Good IDE integration
- Helpful documentation

## Technical Specifications

### Test Organization Structure
```
aviatrix/
├── resource_unit_test_framework.go          # Core framework (existing)
├── resource_unit_test_templates.go          # Templates (existing)
├── resource_unit_test_helpers.go            # Additional helpers (new)
├── resource_unit_test_factories.go          # Test data factories (new)
├── resource_unit_test_assertions.go         # Custom assertions (new)
├── resource_unit_test_scenarios.go          # Mock scenarios (new)
├── resource_aviatrix_account_unit_test.go   # Account tests (expand existing)
├── resource_aviatrix_gateway_unit_test.go   # Gateway tests (new)
├── resource_aviatrix_vpc_unit_test.go       # VPC tests (new)
├── resource_aviatrix_firewall_unit_test.go  # Firewall tests (new)
└── ... (one test file per resource)
```

### Naming Conventions
- Test files: `resource_aviatrix_<resource>_unit_test.go`
- Test functions: `TestResource<Resource>_<Aspect>`
- Sub-tests: Descriptive names in CamelCase
- Mock setups: `setup<Resource><Operation>Mock`
- Factories: `New<Resource>TestData`

## Dependencies and Constraints

### Dependencies
- Go 1.23+ with testing package
- Terraform Plugin SDK v2
- testify/assert library
- moq for mock generation
- GitHub Actions for CI/CD
- Coverage reporting tool (codecov/coveralls)

### Constraints
- Must maintain backward compatibility with existing tests
- Cannot modify production code unless fixing bugs
- Must not introduce external dependencies to production code
- Test execution time must stay under 2 minutes
- No credentials or sensitive data in test code

## Risk Assessment

### High Risk
- **Mock regeneration breaking existing tests**
  - Mitigation: Incremental regeneration, extensive validation

- **CI/CD integration causing pipeline failures**
  - Mitigation: Gradual rollout, feature flags, parallel testing

### Medium Risk
- **Coverage requirements too strict causing developer friction**
  - Mitigation: Gradual threshold increases, exemption process

- **Test maintenance burden for 100+ resources**
  - Mitigation: Templates and automation, good documentation

### Low Risk
- **Performance degradation with full suite**
  - Mitigation: Parallel execution, performance monitoring

- **Flaky tests causing CI failures**
  - Mitigation: Strict test isolation, no external dependencies

## Glossary

- **Unit Test**: Fast, isolated test with no external dependencies
- **Acceptance Test**: Integration test requiring real infrastructure (TF_ACC=1)
- **Mock**: Simulated object replacing real dependencies
- **Coverage**: Percentage of code executed by tests
- **CRUD**: Create, Read, Update, Delete operations
- **Schema Validation**: Testing resource schema configuration
- **Input Validation**: Testing user input validation functions
- **State Management**: Testing Terraform state handling
